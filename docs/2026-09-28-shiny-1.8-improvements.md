# What Shiny for Python 1.8 offers shiny_deckgl that it does not use yet (2026-09-28)

Shiny 1.8.0 (13 Sep 2026) is still the latest release; nothing newer is on PyPI. The
2026-09-27 dependency review took the 1.8.0 headline items (`session.allow_reconnect()`,
`shiny.testserver`, `output_text_verbatim` deprecation) — all done in 1.12.x. This pass reads
the whole 1.3 → 1.8 changelog against the code and lists what the package still does not use,
with the concrete API (checked in the installed 1.8.0 source) and what it would buy.

Already used: `HTMLDependency` (`head_includes()`), `reactive.extended_task`,
`render.download_button`, `session.allow_reconnect`, `shiny.testserver`, `ui.output_code`.

## Ranked proposals

### 1. Request/response RPC instead of input juggling — `session.set_message_handler()` (0.9)

`Shiny.shinyapp.makeRequest(name, args, onSuccess, onError)` on the client calls a Python
handler registered with `session.set_message_handler(name, fn)` and gets its return value back.
Handlers run in an isolated reactive context.

Today several client→server flows are modelled as *inputs* with a `requestId` the app has to
match: `query_rendered_features` → `_query_result`, `export_image` → `_export_result`,
`has_image` → `_has_image`. The inverse (server asks the map) does not exist at all.

Buys: `await widget.query_rendered_features(session, point=...)` **returning** the features;
`await widget.export_image(session)` returning the PNG bytes; `await widget.get_view_state(session)`
/ `get_bounds()` without waiting for a `moveend`. Implementation: one handler per map,
`session.set_message_handler(f"{id}_rpc", ...)` for server-side, and for client-side calls a
small `deck_request` message whose reply the JS sends via `makeRequest("shiny_deckgl_reply", ...)`.
The existing input-based flows stay for backward compatibility.

### 2. Bookmarking of the map — `App(bookmark_store=)` + `session.bookmark` (1.4; needs ≥ 1.6.4)

Shiny serialises every input into the bookmark, so `<id>_view_state`, `_legend_visibility`,
`_click`, `_hover`, `_drawn_features` … are stored — but on restore nothing moves the map, and the
hover/click payloads bloat the URL. `session.bookmark.on_restored(fn(RestoreState))` runs after
inputs are restored; `session.bookmark.exclude` drops inputs; `on_bookmark(fn(BookmarkState))`
can add `state.values`.

Proposal: `MapWidget.enable_bookmarking(session, *, layers=True)`:
- exclude `_click`, `_hover`, `_map_click`, `_map_contextmenu`, `_query_result`,
  `_export_result`, `_widget_event`, `_reconnected` (transient);
- `on_bookmark`: write the per-session snapshot's layer visibility (already kept for
  `resend_last_update()`) and the current style into `state.values[id]`;
- `on_restored`: `fly_to(state.input[view_state_input_id])` (0 ms), `set_style`,
  `set_layer_visibility(state.values[id]["visible"])`.
Requires `shiny >= 1.6.4` for this feature (1.6.4 fixed a path-traversal bug in bookmark restore,
CWE-22); guard with a version check and a clear error, keep the runtime floor at 1.6.3.

### 3. Large payloads over HTTP — `session.dynamic_route()` 

`session.dynamic_route(name, handler: Callable[[Request], ASGIApp]) -> url` serves a
session-scoped URL. The trips demo sends ~20 MB layer payloads through the websocket as one
custom message; the reconnect snapshot re-sends them. With a route, `update()` could send
`{"layers_url": "/session/<id>/dynamic_route/<name>"}` and the runtime `fetch()`es the JSON
(or the binary attribute buffers — see `shiny-deckgl-binary-mesh-transport.md`) in parallel with
rendering, with HTTP caching and no websocket frame-size pressure.

Proposal: `MapWidget.update(..., transport="auto")` — payloads above a threshold (say 2 MB
serialised) go via a dynamic route; the message carries the URL and a content hash so the
runtime can skip an unchanged fetch. Ships as opt-in first (`transport="http"`).

### 4. Dark mode ↔ basemap/theme — `ui.input_dark_mode(id=)` (0.8)

`input_dark_mode(id="mode")` reports `"light"`/`"dark"` in `input.mode()` and sets
`data-bs-theme` on `<html>`. Nothing in the package reacts to it: a dark app shows a light
Positron basemap and light deck widgets.

Proposal: `MapWidget(dark_style=...)` plus a runtime `MutationObserver` on
`document.documentElement[data-bs-theme]` that swaps the style (`set_style` semantics, native
layers re-added) and passes `theme` to deck's widgets (`_ThemeWidget` supports `light`/`dark`;
deck 9.4 widget CSS has `deck-widget-dark`). Server-side alternative for apps that want control:
`await widget.set_dark_mode(session, input.mode() == "dark")`. Demo: add `ui.input_dark_mode(id="mode")`
to the navbar.

### 5. Official test helpers — `shiny.pytest.create_app_fixture`, `shiny.playwright.controller.UiBase` (1.0)

`tests/_e2e_app.py` hand-rolls what `create_app_fixture(app_path, scope="module")` does
(process start, port, URL, teardown), and every browser test re-implements
`window.__deckgl_instances[...]` probes. Shiny ships `UiBase(page, id=, loc=)` for controllers.

Proposal: `shiny_deckgl.testing.MapWidgetController(page, id)` with `expect_layers([...])`,
`expect_layer_visible(id, bool)`, `expect_widget(class)`, `click_legend(layer_id)`,
`view_state()`, `wait_ready()` — used by the package's own e2e tests and importable by users'
Playwright suites. Migrate `_e2e_app.running_app` to `create_app_fixture`. Also `local_server`
(1.8.0 pytest fixture) for `tests/test_demo_headless.py`.

### 6. Test-mode snapshots — `App(test_mode=)`, `input.set_snapshot_preprocess()` (1.7)

With `SHINY_TESTMODE=1`, `/session/{id}/dataobj/shinytest` dumps every input; our `_view_state`,
`_click` … land there verbatim, and a 20 MB `_drawn_features` or a float-noisy `_view_state`
makes snapshots useless. `session.set_snapshot_preprocess(id, fn)` scrubs a value for the
snapshot only.

Proposal: `MapWidget` registers preprocessors for its inputs on first `update()` (round
`view_state` to 4 dp, replace `object` in `_click`/`_hover` by its keys, drop `requestId`s), and
`shiny.testmode.export_test_values(**{f"{id}_layers": lambda: [...ids...]})` exposes the layer
ids and visibility so `AppTestValues` can assert on the map without a browser.

### 7. Module hygiene — `session.on_destroy()` / `session.destroy(id)` (1.6.1–1.6.3)

Per-session state (`_session_styles`, `_session_state`) is a `WeakKeyDictionary` keyed by the
session object; a module scope destroyed with `session.destroy(id)` keeps its parent session
alive, so a map created inside a destroyed module keeps its snapshot (incl. layer data) until the
root session ends. Proposal: in `MapWidget.__init__`-time helpers that take a session, register
`session.on_destroy(lambda: self._forget(session))` once per session (cheap; also lets
`resend_last_update()` return `False` for a destroyed module).

### 8. Standalone pages — `ui.page_html()` (1.8.0)

`App(ui=ui.page_html(html, extra_deps=[head_includes()]))` serves a hand-written or exported
HTML document with Shiny's dependencies injected. `to_html()` already produces a static page;
a `to_shiny_page()` variant that emits the placeholder `<meta name="shiny-dependency-placeholder">`
and keeps the `<div class="deckgl-map">` would let an exported map become a *live* Shiny app
with one line — useful for the "export then keep editing" workflow the Export tab shows.

### 9. Demo-only niceties (no library change)

- `ui.offcanvas()` (1.7) sliding panel for the 34 layer switches instead of the long sidebar.
- `ui.toast()` (1.5.1) for export/query status instead of the download-generator log line
  (review finding D8).
- `ui.toolbar()` (1.6) above the map for the zoom/step/preset buttons.
- `ui.input_dark_mode(id="mode")` once #4 exists.
- `session.clientdata.pixelratio()` (1.3) to pick `useDevicePixels`/`pixelRatio` per client, and
  `clientdata.url_search()` for deep links until bookmarking (#2) lands.

### 10. Observability — `shiny.otel` (1.6)

`@otel.suppress` on the hot path (`update()` serialisation, `partial_update()`) and span
attributes for payload size / layer count when collection is on. Small, optional.

## Not worth doing

- `ui.Chat`/`MarkdownStream` (now `shinychat`): no fit.
- Express mode: `MapWidget.ui()` returns a `Tag`, so it already works in Express; a docs example
  is enough.
- Custom output renderer (`render.renderer.Renderer`): making the map an *output* would make
  every layer change a full re-render and lose `partial_update`/visibility patching; the
  custom-message design is the right one for a map.

## Suggested order

1 (RPC) and 4 (dark mode) are user-visible and small; 2 (bookmarking) and 3 (HTTP transport) are
the substantial features for a 1.13; 5–7 harden the test story on top of the CI work done today.
