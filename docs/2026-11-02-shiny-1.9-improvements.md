# Shiny for Python 1.9 — what it changes for shiny_deckgl (2026-11-02)

Shiny 1.9.0 was released 29 Oct 2026 and is on PyPI and conda-forge. The `shiny` env still
has 1.8.0. Unlike 1.8, this release is mostly **one behavioural change** — reactive effects
run concurrently and the session's receive loop no longer waits for the flush — plus a few
small features. This pass reads the 1.9.0 changelog and the 1.9.0 wheel source
(`shiny/session/_session.py` `_run_impl`, `run_once_when_idle`) against the code and checks
the claims empirically.

## Compatibility verdict: nothing breaks

Tested with the 1.9.0 wheel prepended to `PYTHONPATH` (env untouched; narwhals 2.16 < the
2.26 pin only matters to `render.data_frame`, which the package does not use):

| Suite | Result on 1.9.0 |
|---|---|
| Unit (all non-browser tests) | 2131 passed, 12 skipped |
| `test_e2e_rpc` / `_viewport` / `_http_transport` / `_bookmark` | 2 / 3 / 3 / 1 passed (before this change; with it, `test_e2e_rpc` has 3, incl. the plain-effect case) |

Not used by the package, so the breaking items do not apply: `reactive.lock()`,
`reactive.on_flushed()`, `session.on_flush()`, `shiny.plotutils.near_points`, `shiny.otel`,
`Jsonifiable`, `shiny add test`. `DenialContext` still lives at
`shiny.reactive._extended_task` (the RPC guard's import still resolves). No CSS, JS or test
selects the sidebar's `<aside>`, so its change to `<div>` is invisible.

## Ranked proposals

### 1. `MapWidget.rpc()` can be awaited inside effects on 1.9 — relax the guard (version-gated)

*Implemented in [Unreleased] (with #2 and #5).*

`_refuse_rpc_inside_flush()` (`map_widget.py:225`) raises when `rpc()` is called from an
effect/calc/render, because in ≤ 1.8 the session loop awaited the flush inline, so the
browser's `makeRequest` reply could never be read. In 1.9 `_run_impl` queues `update`
(input) messages with `run_once_when_idle()` but runs `tag`/`args` messages (our
`<id>_rpc_reply`) in their own `asyncio.create_task(self._dispatch(...))` immediately.

Discriminating probe (guard monkeypatched away, `await m.rpc(session, "getViewState")`
inside a plain `@reactive.effect`, real browser):

| Shiny | Result |
|---|---|
| 1.8.0 | `TimeoutError` after 5 s — the deadlock is real, the guard is justified |
| 1.9.0 | `OK zoom=6.0` — reply arrives |

Proposal: keep the raise for Shiny < 1.9, skip it on ≥ 1.9. Feature-detect rather than
parse versions: `hasattr(session, "run_once_when_idle")` (new in 1.9, appears together
with the concurrent loop). Then the natural code works:

```python
@reactive.effect
@reactive.event(input.ask)
async def _():
    vs = await widget.get_view_state(session)
```

Caveat to document: while the effect awaits the reply, the session is busy and its input
changes queue (by design in 1.9), so a slow `exportImage` delays that session's other
reactions; `extended_task` remains the better call site for slow methods.

The guard then needs the `session` (today it takes no argument and `rpc()` calls it before
`_rpc_state(session)`). The fake session in `tests/test_rpc.py:30` has no
`run_once_when_idle`, so the existing refusal test keeps passing unchanged on 1.8 and 1.9;
add a second test with a fake that exposes `run_once_when_idle` and assert the guard does
**not** raise.

Text that states the deadlock as unconditional and needs a "Shiny < 1.9" qualifier:
`map_widget.py` (`_refuse_rpc_inside_flush` docstring, `rpc()` docstring, the
`TimeoutError` message), `tests/test_rpc.py` module docstring, `docs/api_reference.md:2804`,
`README.md:134` ("a plain effect is refused (it would deadlock)"). `CHANGELOG.md` history
stays as is.

Also: in `rpc()`, move `st["pending"].pop(request_id, None)` into a `finally`. In 1.9
`effect.destroy()` / `session.destroy(id)` cancel in-progress async effects (CancelledError at
the current `await`), and a cancelled call currently leaves its future in `pending`. Tiny leak,
one-line fix.

### 2. Stale "global reactive lock" rationale — update the comments, keep the design

`_viewport.py:163-168`, `tests/test_e2e_viewport.py:4` and
`docs/2026-09-26-codebase-review.md:343` justify rescheduling instead of sleeping by "Shiny
runs effects under its global reactive lock". That lock is gone in 1.9 (`reactive.lock()` is
defunct). The design is **still right** for a new reason: a sleeping effect keeps its
session busy, and in 1.9 that session's newer viewport inputs queue until idle, so a newer
request still could not supersede the sleep. Reword to cover both versions; no code change.

### 3. Effect concurrency within one widget — audited, no change needed

Two async effects touching the same map can now interleave at `await`s. Checked:
`update()`, `partial_update()` and `set_layer_visibility()` merge into the per-session
reconnect snapshot **synchronously, immediately before their single `await
send_custom_message`** (`map_widget.py:655-657`, `1040-1041`, `1113-1114`), so snapshot order
and wire order can only diverge if the ASGI server reorders two sends (in practice
uvicorn/websockets write the frame in call order before yielding to drain — an
implementation property, not a documented guarantee).
`_send_update`'s HTTP path mutates `http_state` (`seq`, `data`) before its one await; a
cancel lands after the mutation, never mid-way. Two in-flight HTTP updates serve the latest
`data` under both URLs (latest-wins), as before. Runs of the *same* effect still do not
overlap, so `_viewport_runner` and `_auto_advance` keep their guarantees. The user-visible
change: the **order between different effects** that both call `widget.update()` is now
"whoever finishes awaiting first" rather than effect order. Worth one sentence in the user
manual, not code.

### 4. Demo export log now updates during the download — closes review finding D8 for free

`export_html` (`_app_server.py:1095`) sets `_export_log` inside the
`@render.download_button` generator. Before 1.9 the "HTML exported…" text appeared only after
the next client message; 1.9 (#1785) flushes it right away. *Decided: no code change. The
demo is a core app with a hand-placed `ui.download_button` whose label already carries an
emoji like every other button; 1.9's `icon=` targets Express's auto-placed button, so it
would only duplicate the emoji.* (Originally proposed: use the new
`icon=` argument (any icon tag; `faicons` is not a dependency, so an inline
bootstrap-icon `ui.HTML` / `ui.tags.i(class_="bi bi-download")`) on that button and on
`ui.download_button` at `_app_ui.py:855`.)

### 5. `session.run_once_when_idle(fn)` — docs note, no package use

The package and demo never set a `reactive.Value` from outside the graph (no threads or
`create_task`; the one `asyncio.to_thread` runs inside an `extended_task` and returns a
value). Add a short note to the user manual's "animation / background data" section: apps
that push data from a timer or background task should wrap `value.set` in
`session.run_once_when_idle()` (or `loop.call_soon_threadsafe` from a thread). Note: the 1.9
"messages sent outside the reactive graph go out right away" fix concerns `ui.update_*()`
(queued input messages); `send_custom_message` — hence every `widget.*` call — already wrote
straight to the websocket in 1.8 (checked in the installed 1.8.0 source).

### 6. Accessibility: `ui.sidebar(role=...)` in the demo

1.9 makes the sidebar a neutral `<div>` unless `role` is given; `"complementary"` restores
an `<aside>` landmark. **Every** role (`form`, `search`, `complementary`, `region`) is a
landmark and needs an accessible name: without `title`/`aria_label`/`aria_labelledby`, 1.9
raises `ValueError` at UI-build time (`shiny/ui/_sidebar.py:479`), so the demo would fail to
start. The demo's 12 sidebars (`_app_ui.py:60…1466`) could take
`role="complementary", aria_label="<tab> controls"` (or `role="form"` with a name where they
hold only inputs). The `role` argument does not exist before 1.9, so this needs the demo's
Shiny floor raised. Low effort, helps screen-reader navigation.

### 7. Version floors and packaging

- Runtime floor stays `shiny>=1.6.3`; proposal #1 is feature-detected, not a floor bump.
- Test/dev extras (`pyproject.toml:46,62`) can move to `shiny>=1.9.0` once the env is
  updated (`micromamba install -n shiny "shiny>=1.9"`, which pulls narwhals ≥ 2.26,
  `shinychat`, `opentelemetry-api`). Then CI covers both sides of the RPC gate only if one
  job stays on 1.8 — add a 1.8.0 matrix entry, or keep the probe above as a test that
  asserts the refusal on < 1.9 and the reply on ≥ 1.9.
- Windows busy-indicator fix (#1381) applies to the demo's synchronous renders with no change.

## Not worth doing

- `@output_args()` / Express output arguments: the map is not a render output.
- `render.data_frame` speedups, `near_points`, `Progress` fixes: unused.
- otel `reactive_update` span restructure: package emits no spans.

## Suggested order

1 (RPC gate + `finally`) is the only real code change and is small; 2 and 5 are comment and
doc edits that belong in the same PR. 4 and 6 are demo polish. 7 after the env is upgraded.
